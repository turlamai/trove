## Real-machine defects found & fixed (each shipped in a same-day release)

1. **`.plg` XML escaping** (v0.1.1) — bare `&` in inline scripts broke XML parsing.
2. **Same-origin check vs `host:port`** (v0.1.2) — every request on a
   non-default port was rejected; `HTTP_HOST` keeps the port, `parse_url`
   does not.
3. **Unraid 7 nginx CSRF layer** (v0.1.2/v2026.11.30) — nginx silently
   drops POSTs whose `csrf_token` body field mismatches the rotated
   `var.ini` token; gateway + client adapted (dual-token, refresh+replay).
4. **Version comparison** (v2026.11.26) — plugin manager compares versions
   as strings; `0.1.10` sorted below `0.1.9` ("not installing older
   version"). Switched to `YYYY.MM.DD`.
5. **Root-level listings** (v0.1.3) — empty final component (share root)
   failed with ENOENT.
6. **php-fpm opcache staleness** (v0.1.7) — the gateway's bytecode never
   revalidated; endpoint renamed to `gateway.php` (fresh compile path).
7. **Daemon never restarted on upgrade** (v0.1.4→v2026.11.28) — the old
   process stayed alive across binary replacements; `start-daemon.sh
   --restart` + post-install hook.
8. **Fatal double-unlock in the dispatch loop** (v2026.11.28) — killed the
   daemon the moment the first job dispatched; found via goroutine dump in
   `/var/log/troved.log` (debug endpoint shipped to read it remotely).
9. **`renameat2` flags unsupported on shfs** (v2026.12.02) — user shares
   are FUSE; every copy commit failed after a fully verified staging
   write. Existence-probe + plain-rename fallback.
10. **Skip policy surfaced as hard failure** (v2026.11.29/2026.12.01) — a
    source replaced under a skip policy failed the job instead of
    completing with warnings.
11. **Delete manifests missing `SourceRoot`** (v2026.12.04) — every real
    delete died with ROOT_NOT_FOUND; unit tests built manifests by hand
    and missed the contract gap.

## Environment observations (not Trove bugs)

- The share used for acceptance is **Cache: Yes** and a mover schedule is
  active: empty directories on cache disappear within minutes (mover
  cleans emptied dirs), and during mover activity shfs path resolution
  can transiently fail for files that just moved cache→array. Trove
  fail-closes in every case (NOT_FOUND surfaced, source untouched).
- shfs does not support `renameat2` flags or `utimensat(AT_EMPTY_PATH)`
  timestamp preservation on this setup; the latter is a recorded warning,
  not an error.

Defects caught by this pass (each shipped same day):

1. `shares_revoke` route tuple malformed (3 elements instead of 4) — every revoke 404'd (2026.12.16).
2. `.plg` CHANGES contained a bare `<dataDir>` — malformed XML took the install manifest down until re-tagged (2026.12.16→fixed, tag re-pushed).
3. Release workflow's manifest write-back failed the whole job when main moved during the build; rebase-and-retry added, manifest landed manually.
4. Share dialog received the inspector's parent-directory path — links targeted an empty path (2026.12.17).
5. Folder ZIP had no UI entry at all (2026.12.17).
6. Dashboard tile linked to the retired SHARES embed (2026.12.18).
7. No settings surface to enable the share listener (2026.12.19); the save used the GET-only read route and always 405'd (2026.12.20).
8. Share store never created `<dataDir>/trove-shares/` — first create failed ENOENT (2026.12.20).
9. Share creation ignored the client's `rootId` string — records persisted with an empty root (2026.12.21).
10. Media streaming rode the buffered JSON forward: whole file in PHP memory, Range/206 semantics lost (2026.12.22), then the relay's status-line regex missed the reason phrase and answered 200 instead of 206 (2026.12.23).
11. ZIP/file downloads lost Content-Type/Disposition in the forward — archives saved as gateway.json (2026.12.24).

Not exercisable from off-site (by design — the listener is LAN-only):
an actual public-link download with password/expiry enforcement. The
resolve path shares the store's constant-time password check and the
same `http.ServeContent` machinery verified above; LAN-side behavior is
left as a 2-minute user check.

## Display form (final, v2026.12.13)

The 7.3 responsive nav renders its core sections (DASHBOARD…TOOLS) from
the WebGUI app itself and does not pick up third-party top-level
sections — an xmenu page with Menu="Trove" gets a working standalone
URL (/Trove/trove) but no nav entry. Final native presentation:
**Tools → Trove** opens the standalone full-width page (same layout as
the old /Tools/trove, page chrome owned by the WebGUI), **Settings →
Trove** for configuration, a **Dashboard tile** for at-a-glance status,
and the page itself is full-screen with the compact pane toggle in its
top-right corner. (A true top-level nav section would require patching
core WebGUI files — out of scope by our own red line.)
